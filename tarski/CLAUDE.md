# CLAUDE.md

## What this package is

Tarski is lakatos's JS-semantics library: the Lean definitions that give TypeScript's values and operations their meaning. `lakatos prove` (thales) proves `@ensures` properties against models built from these definitions. The package is shared: thales requires it by path (`require tarski from "../../tarski"` in `engines/thales/lakefile.lean`); no engine may be required by it. The boundary rule: nothing here mentions `ThalesDsl` or any emission concern — lakatos owns syntax and search, this library owns meaning.

It holds two things over one set of definitions. `Js/` is the semantics library. `Tarski/` is an evaluator for a fragment of JavaScript — a definitional interpreter whose every primitive operation _is_ one of the library's, so a `Theorem` and a run appeal to the same meaning. The evaluator's parser is not in Lean: `frontend/` is a TypeScript bridge over tsc that emits ESTree JSON, and `schemas/tarski-estree.schema.json` at the repo root is the seam. Growing the evaluator is GitHub epic #376.

The Lean toolchain pin is `lean-toolchain` here; `engines/thales/lean-toolchain` is a symlink to it. `lake-manifest.json` is tracked.

## Common commands

From `tarski/`:

```bash
lake build                          # the Js library, the evaluator, the binary
lake build tarski                   # just the evaluator's binary
lake build TarskiTest               # the Lean tests under Test/Js/ and Test/Tarski/
lake env lean Test/Js/NormTest.lean # one test file in isolation
sh scripts/check-boundary.sh        # the evaluator's arithmetic boundary
```

And the test262 runner, which is TypeScript and so needs `npm run build`
from the repo root first:

```bash
node scripts/setup-test262.js       # clone the pin into .test262 (or set LAKATOS_TEST262)
node ../dist/tarski/frontend/src/test262/cli.js test/harness
node ../dist/tarski/frontend/src/test262/cli.js test/harness \
  test/built-ins/Number test/built-ins/Math test/built-ins/Boolean \
  --check test262/expected.json
sh scripts/test262-full.sh          # the scheduled full run; writes test262/results.{md,json}
```

`LAKATOS_TEST262` names a checkout to read instead of `.test262`, and the
runner labels a results table with the commit that checkout is really at.
`TEST262_TIMEOUT_MS` (default 10000) and `TEST262_BUDGET_MS` (default
14400000, four hours) are what `test262-full.sh` passes as `--timeout` and
`--budget`.

The installed name is `tarski-test262`, a `bin` of the root package. npm
does not link a package's own bins, so in a checkout the spelling is the
`node dist/…` one above; `npx tarski-test262` works once lakatos is
installed or linked.

The binary lands at `.lake/build/bin/tarski` and takes one ESTree document:

```bash
node ../dist/tarski/frontend/src/bridge-cli.js t.js t.json   # after npm run build
.lake/build/bin/tarski run t.json
```

The bridge and its tests are part of the repo-root npm package, not this lake package: build, typecheck, test, and format them from the repo root.

Wrap `lake env lean` in a timeout when running it by hand; a bad artifact can grind indefinitely.

| `Tarski/Eval.lean`          | The interpreter: one `mutual` block under `partial_fixpoint`, so its equations are theorems and no fuel parameter exists. Primitive operations delegate to `Js`. What **never joins a simp set** is what recurses on something other than syntax: **`evalWhile`, `getProp`, `protoChainHas`, and `joinElements`**, each unfolded one step at a time with `rw`. **ToPrimitive takes a hint**: `+`, the relations, and the unary operators pass `number`, while `String(v)`, `join`, and ToPropertyKey pass `string`, and **`toStringValue` is ToString on values**. ## Tests

`Test/Js/` and `Test/Tarski/` — Lean unit tests, one file per concern; `lake build TarskiTest` builds them all and each runs alone via `lake env lean`. Library test files import only `Js` and its submodules.

`Test/Tarski/fixtures/numeric-loop.json`, `counter.json`, `errors.json`, `uncaught.json`, `harness-floor.json`, `compare-array.json`, and `print.json` are the parser bridge's output byte for byte; `tarski/frontend/tests/bridge-cli.test.ts` holds the two copies of each together, and the tarski workflow runs the binary on all eight. `print.json` prints `a`, `2`, `t` and then the last statement's completion value. `number-math.json`, #382's example, is the eighth, and prints `true`. `counter.json` is #378's own example and prints `true`; `errors.json` is #379's and prints `zero!`; `harness-floor.json` is #380's and `compare-array.json` is the test262 harness's `compareArray`, both printing `true`; `uncaught.json` is the one that fails — `Uncaught TypeError: not a function` on stderr, exit 1. The bridge's own tests are vitest, run from the repo root.

The runner's vitest suites (`frontend/tests/test262-*.test.ts`) run against `frontend/tests/fixtures/test262/`, a fake tree with one directory per outcome class, and `frontend/tests/fixtures/fake-tarski.mjs`, a stand-in binary that obeys a marker literal in the document it is handed. `test262-e2e.test.ts`, under `LAKATOS_TARSKI_E2E=1`, runs the _real_ binary over the same tree and demands the same table; that is what ties the fake's exit codes to the contract they transcribe, and `tarski.yml` — which now installs Node — runs it.

The whole-suite mode is tested over that same fake tree: `--summary`'s progress lines, `--budget 0` (the one budget under which no test is spawned at all, so the arm needs no clock), and `--markdown`/`--json` against a copy of the tree that has been `git init`-ed, which is how the commit label and the off-the-pin warning are exercised. **`renderMarkdown` is held prettier-clean by prettier itself** — `format(renderMarkdown(s), { parser: "markdown" })` must equal its input — because `results.md` is committed and so checked by the `Format` job like every other Markdown file here, rather than exempted from it. The committed `results.json` and `results.md` are read back by `test262-cli.test.ts`: that is what holds the table to the pin, the runner itself only warning when a checkout is somewhere else.

**The committed table for `test/harness` is 0 pass, 99 unsupported, 17 not-run, and that is honest.** The suite's own `assert.js` opens with a `switch` and goes on to `var`, `for`, `Object.prototype.toString.call`, `Array.prototype.map.call`, and `JSON`, so every non-`async` test in the slice is refused at the first of those; `switch` and `var` are #393's, `for` is #383's. Transcribing the harness would defeat the point of running the official suite. The numbers ratchet as the syntax lands.

**`test/built-ins/Number`, `Math`, and `Boolean` are committed the same way: 718 tests, all `unsupported`, 0 not-run, across 69 rows** — for the same reason, since every one of them loads `assert.js` too. That floor ratchets with #393 and #383, not with this slice.

What is behind that floor was measured, not guessed. A **diagnostic run** — the pin's `harness/` with `assert.js` replaced by the fragment version in `frontend/tests/fixtures/test262/harness/`, which is not committed anywhere and is not the suite — answers **168 pass, 246 fail, 304 unsupported**. The unsupported are `var` (280), `for` (6), and then single digits of `delete`, `void`, `for`-`in`, `==`, postfix `++`, a generator, and a BigInt literal. The 246 failures classify as:

| 50    | the diagnostic harness's own `assert.sameValue`, which is `===` rather than SameValue, comparing a NaN to a NaN — these pass under the suite's `assert.js` and are an artifact of the measurement |
| 38    | StringToNumber: `Number("12")` is NaN (#388)                                                                                                                                                      |
| 36    | `isConstructor.js` and function `length`, which need `Reflect.construct` and descriptors (#389)                                                                                                   |
| 28    | descriptors through `propertyHelper.js` (#389)                                                                                                                                                    |
| 20    | `toFixed`, `toPrecision`, `toExponential`, and `toLocaleString`, absent members (#388)                                                                                                            |
| 5     | symbols (#392)                                                                                                                                                                                    |
| 3     | `new String(…)`, the String wrapper (#391)                                                                                                                                                        |
| 2     | `Object.prototype.toString`/`valueOf` (#389)                                                                                                                                                      |

Not one of them is a `Math` or `Number` operation answering the wrong number. The one wrong answer this slice ships on purpose is `Math.pow` and `**` of a non-integral exponent (#434), and `Number.prototype.toString`'s radix output (#388); no test in these three directories reaches either without first needing `var`.
